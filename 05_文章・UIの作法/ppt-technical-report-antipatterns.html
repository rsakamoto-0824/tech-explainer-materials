Anti-Patterns Catalog

技術報告パワーポイント資料の
アンチパターン集

技術報告会・社内発表・学会発表で「伝わらない」スライドを生む典型パターンと、その改善策をまとめたガイドです。 各項目は「悪い例 → 良い例 → なぜそうするか」の順で整理しています。

1. 情報量の過多

1枚のスライドに詰め込みすぎる、聴衆が読みきれない状態を作るパターンです。

AP-1.11スライドに伝えたいことが3つ以上ある

悪い例

  • 「背景」「課題」「手法」「結果」「考察」が1枚に詰まっている
  • 箇条書きが10項目以上ある
  • 文字を読まないとスライドの主張が分からない

良い例

  • 1スライド = 1メッセージ(One Slide, One Message)を徹底する
  • 箇条書きは多くても5項目までに絞る
  • スライドタイトルだけ読めば論旨が追える

なぜ：人間が短時間で処理できる情報量には限界があり、口頭説明とスライドの両方を同時に追わせると理解が止まる。

AP-1.2文章をそのまま貼り付けている

悪い例

  • 報告書やメールの文章をコピペした長文がスライドを占有
  • 句読点付きの完成された段落が複数並ぶ
  • 発表者が読み上げる時間、聴衆が文字を読んでいる

良い例

  • キーワードと短文(20字以内)に分解する
  • 文章で伝えたい内容は配布資料や Appendix に回す
  • スライドは「視覚的サマリ」と割り切る

なぜ：スライドは「読む資料」ではなく「見る資料」。長文は配布資料の役割で、発表中は集中を奪うノイズになる。

2. フォントと文字サイズ

「会場の後ろからでは読めない」最大の原因になる項目です。

AP-2.1本文が18pt未満

悪い例

  • 本文10〜12ptで「情報を多く載せたい」を優先
  • 注釈が6〜8ptで実質読めない
  • 会議室後方の聴衆が前傾姿勢になる

良い例

  • 本文は最低 18pt、推奨 20〜24pt
  • タイトルは 28〜36pt
  • 注釈でも 14pt を下限にする

なぜ：プロジェクター投影では PC 画面より見かけが小さくなる。サイズ不足の文字は「載せていない」のと同じ。

AP-2.2フォントが混在している

悪い例

  • 明朝・ゴシック・MSゴシック・メイリオが混ざる
  • 本文と図中文字でフォントが違う
  • 欧文に和文フォントが当たって不格好

良い例

  • 和文は「メイリオ」または「游ゴシック」に統一
  • 欧文は「Segoe UI」「Arial」など対応フォントを指定
  • スライドマスターで一括設定して事故を防ぐ

なぜ：フォントの揺れは「資料に手間がかかっていない」という無意識のシグナルになり、内容の説得力まで損なう。

3. 配色とコントラスト

投影環境では PC 画面と見え方が大きく変わります。色の使い方は読みやすさに直結します。

AP-3.1色を5色以上使う

悪い例

  • 強調したい箇所すべてに違う色を当てる
  • 赤・青・緑・橙・紫が1枚に同時登場
  • どこが本当に重要なのか分からない

良い例

  • 基本色は3色まで(主色・補助色・強調色)
  • 強調色は1スライドに1〜2箇所だけ使う
  • テーマカラーをスライドマスターで固定する

なぜ：「全部が強調」は「何も強調されていない」と同じ。色は希少資源として扱う。

AP-3.2背景と文字のコントラストが不足

悪い例

  • 薄いグレー背景に薄いグレー文字
  • 青背景に黒文字、赤背景に緑文字
  • 写真背景の上に白文字を直置きして埋没

良い例

  • 白背景+濃紺文字、紺背景+白文字を基本に
  • WCAG 基準で 4.5:1 以上のコントラスト比を確保
  • 写真背景には半透明オーバーレイを敷く

なぜ：プロジェクターは外光や色温度で見え方が変わる。手元で OK でも会場で読めないケースが多い。

AP-3.3赤緑だけで状態を区別する

悪い例

  • OK=緑、NG=赤 のみで判別させる
  • 色弱の聴衆には差が見えない

良い例

  • 色 + 記号(◯/×) + テキストラベルを併用
  • カラーユニバーサルデザイン対応色(青/橙)を選ぶ

なぜ：男性の約5%は色弱を持つ。技術報告は意思決定資料なので、誰一人として情報を取り逃さない設計が必要。

4. レイアウトと余白

「窮屈なスライド」は内容より先に読み手を疲れさせます。

AP-4.1端まで要素を詰める

悪い例

  • 左端から右端まで図やテキストを敷き詰める
  • 余白=もったいない、と考えてしまう

良い例

  • 外周には最低 5% 程度の余白を取る
  • 要素同士のグルーピングが分かる間隔をとる

なぜ：余白は「情報の境界」を伝える役割を持つ。情報そのものと同じくらい重要なデザイン要素。

AP-4.2整列が崩れている

悪い例

  • テキストボックスの左端が数ピクセルずつズレている
  • ボックスサイズがバラバラで揃って見えない

良い例

  • ガイド線・スマートガイドを使って左揃え/中央揃えを徹底
  • 同じ役割の要素はサイズも統一する

なぜ：整列の乱れは無意識のストレスを生み、内容への信頼を下げる。技術報告では特に「正確さ」の印象に直結する。

5. 図表とイメージ

技術報告では図表が主役。図解の品質がそのまま伝達速度に直結します。

AP-5.1スクリーンショットを拡大して荒い

悪い例

  • Excel 表をスクショして引き伸ばす
  • UI 画像がボケて文字が判読不能

良い例

  • 表は PowerPoint 内で作り直す(再描画される)
  • UI は必要部分のみトリミングして拡大せず使う
  • SVG など解像度に依存しない素材を選ぶ

なぜ：ぼやけた画像は内容を曖昧にし、報告の根拠そのものを疑わせる。

AP-5.2「ご覧の通り」で済ます

悪い例

  • 巨大な表を貼って「詳細は資料を参照」と言って次へ
  • 図のどこを見るべきか示さない

良い例

  • 注目箇所を四角や矢印で明示する
  • 強調以外の部分はグレーアウトする
  • 図の下に「ここから読み取れること」を1行で書く

なぜ：聴衆は資料を初見で見るため、発表者が「読み方」をガイドしない限り誤読される。

6. グラフとデータ表現

数値を扱う技術報告では、グラフが事実認識を左右します。

AP-6.13D グラフを使う

悪い例

  • 3D 円グラフで割合が歪んで見える
  • 3D 棒グラフで奥行きにより値が読みにくい

良い例

  • 2D の棒グラフ、折れ線グラフを基本にする
  • 割合は円グラフより横並びの棒グラフが正確

なぜ：3D 効果は遠近で面積が変わり、数値の正しい比較を妨げる。技術報告に装飾は不要。

AP-6.2軸の起点を 0 にしない

悪い例

  • 差を強調するため Y 軸を 95〜100 にして印象操作
  • 軸ラベルを省略して差が大きく見える

良い例

  • 棒グラフは原則 0 から始める
  • 軸を切り詰める場合は破断記号を入れて明示する
  • 絶対値が重要なら数値ラベルも併記する

なぜ：誤解を生むグラフは「結果の改ざん」と同等に扱われる。意図的でなくても信頼を失う。

AP-6.3凡例が遠い・順序が無関係

悪い例

  • 折れ線とは別の場所に凡例ボックスが置かれる
  • 凡例の順序がグラフ上の系列順と一致しない

良い例

  • 系列名を線・棒の末尾に直接ラベル付け
  • 凡例を残す場合は系列の並びと一致させる

なぜ：視線移動が増えるほど読解スピードが落ちる。情報は「物理的に近く」配置するのが原則。

7. 数式・記号・単位

技術報告ならではの落とし穴。理系の信頼性は単位と表記でできています。

AP-7.1単位がない

悪い例

  • 「処理時間: 12」「温度: 200」など単位が抜けている
  • グラフ軸に単位が書いていない

良い例

  • 数値の隣に必ず単位を書く(ms, kPa, ℃ など)
  • 軸ラベルは「項目 [単位]」の形式で統一

なぜ：単位を省くと別物の比較になり、結論が変わる。理系資料の最重要マナー。

AP-7.2数式を画像で貼る

悪い例

  • ピンぼけ画像で数式が読めない
  • 後から添字を直せず、結局作り直し

良い例

  • PowerPoint の数式ツール、または LaTeX 連携を使う
  • 変数の意味は数式の下に短く書き添える

なぜ：数式は技術報告の根拠そのもの。可読性と修正性の両方が要る。

8. タイトルと見出し

スライドタイトルは「読み手への要約サービス」です。

AP-8.1タイトルがトピック名のみ

悪い例

  • 「実験結果」「考察」「課題」など名詞だけ
  • タイトルを見ても何が言いたいか分からない

良い例

  • 「条件A では従来比 30% 高速化を確認」
  • 結論または主張を1文で書く(メッセージタイトル)

なぜ：タイトルだけ拾い読みしても話の筋が追えるようにすれば、聴衆の認知負荷が劇的に下がる。

9. ストーリー構成

話の流れが弱いと、スライドが整っていても伝わりません。

AP-9.1背景説明が長すぎる

悪い例

  • 背景・歴史・先行研究で全体の半分を消費
  • 本題に入る前に時間切れ

良い例

  • 背景は「課題」を導く最小限に絞る
  • 聴衆が既に知っている知識は飛ばす
  • 原則として全体の 20% 以内

なぜ：聴衆の関心は「で、何が分かったの?」に向かっている。前段が長いと結論への期待値が下がる。

AP-9.2結論が最後にしか出てこない

悪い例

  • 「結論はこのあと述べます」を多用
  • 聴衆が話の現在地を見失う

良い例

  • 冒頭にエグゼクティブサマリ(結論先出し)を入れる
  • 各章の冒頭にも小結論を置く

なぜ：技術報告の聴衆(管理職・顧客)は時間が限られている。結論先出しは敬意の表明でもある。

10. アニメーションと装飾

「使えるから使う」は失敗のもとです。

AP-10.1派手なアニメーションを多用

悪い例

  • フェード・回転・バウンドが全要素に付く
  • クリックの度に違う動きが出る

良い例

  • アニメーションは「順を追って見せたい時」のみ
  • 効果は「フェード」または「アピール」に統一

なぜ：派手な動きは集中を奪い、内容より動きが記憶に残る。技術報告では原則「静」が良い。

AP-10.2装飾アイコンやイラストの過剰使用

悪い例

  • すべての見出しに無関係なフリー素材アイコン
  • テイストの違うイラストが混在

良い例

  • 意味を持つアイコンだけを残す(ピクトグラム的に)
  • 同じスタイルのアイコンセットで統一

なぜ：装飾は「内容が薄い」シグナルにもなり得る。技術内容で勝負する場では引き算が効く。

11. 引用と出典

外部の図やデータを使う時の作法です。

AP-11.1出典が無い・あいまい

悪い例

  • 「ネットより」「某社資料より」とだけ書く
  • 引用元が不明で再確認ができない

良い例

  • 「著者名(年). タイトル. 出版元.」の形式で明記
  • Web は URL + 取得日を併記する
  • 図表ごとにスライド右下に小さく出典を載せる

なぜ：技術報告で出典不明は致命的。報告全体の信頼度を下げ、コンプライアンス上の問題にもなる。

12. 結論とまとめ

最後のスライドは「次の意思決定」へのバトンです。

AP-12.1「ご清聴ありがとうございました」だけ

悪い例

  • 最終スライドが感謝の言葉のみ
  • 質疑応答の間、何も情報が映っていない

良い例

  • 最終スライドに「結論3点」を残す
  • 質疑中もそのスライドを表示しておく

なぜ：議論はそのスライドを起点に進む。最後の画面が「結論」かどうかで会議の質が変わる。

AP-12.2Next Action が書かれていない

悪い例

  • 結論だけで「次にどうするか」が無い
  • 聴衆が判断を求めているのに、判断材料が揃わない

良い例

  • 「誰が」「いつまでに」「何をする」を1枚に
  • 意思決定が必要な項目には ⭕ で印を付ける

なぜ：技術報告のゴールは「聴衆が次の行動を取れる」こと。結論で終わると会議が宙に浮く。

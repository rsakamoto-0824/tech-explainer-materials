Power BI ダッシュボード開発
TMDL と Power BI Studio の利用手順

Mac の VS Code から Power BI のセマンティックモデルを編集・検証・発行するための手順書です。 2つの拡張は役割がまったく違うため、「どちらで何をするか」を先に固定してから手順に入ります。

対象バージョン
TMDL 1.6.5（publisher: analysis-services）／ Power BI Studio 2.11.1（publisher: GerhardBrueckl）
確認環境
macOS 26.6.2 ／ Apple M1 ／ .NET Runtime 10.0.11 導入済み
対象リポジトリ
litho-overlay-dashboard ／ PowerBI_LithoBooster_DashBoard（.tmdl 計26ファイル）
本資料の根拠
両拡張の定義ファイル・README、および実際のリポジトリの TMDL ファイルから確認

0. 2つの拡張の守備範囲

名前が似ているので混同しがちですが、この2つはまったく別の道具です。片方はテキストエディタの支援、もう片方はサーバーとの通信手段です。

TMDL 書くための拡張

正体

言語サポートのみ。コマンドは0個

  • .tmdl / .tmd の色分けと入力補完
  • DAX の整形
  • フォルダ全体の構文チェック（既定はオフ）
  • 通信はしない。ローカルのファイルを扱うだけ

Power BI Studio つなぐための拡張

正体

Power BI サービスの操作卓。コマンド63個

  • ワークスペース／データセット／レポートの一覧と操作
  • サービス上のモデルを直接 TMDL で編集・検証・発行
  • 更新の実行・スケジュール設定・パラメーター更新
  • DAX / REST API を実行するノートブック
💡Mac 環境ではこの組み合わせが特に重要

Power BI Desktop は Windows 専用で、Mac には存在しません。そのため Mac 上でモデル定義を触る手段は実質この2つだけです。TMDL拡張で安全にテキストを書き、Power BI Studio でサービスへ送る、という分担になります。

1. 前提の確認

1-1 TMDL機能を使うための前提（ここが最初の関門）

Power BI Studio の TMDL 機能に必要なもの
前提この環境の状態補足
.NET Runtime 7 以上✅ 10.0.11 が導入済みTMDL操作は .NET製の補助プログラム（TMDL Proxy）が担当するため必須
Power BI サービスのアカウント要確認組織のテナントへサインインする
API権限要確認Workspace.Read.All / Dataset.Read.All / Dataset.ReadWrite.All
ワークスペースのXMLAエンドポイント要確認読み書きするには Premium / PPU / Fabric 容量が必要。共有容量では TMDL の発行はできない
🛑導入前に社内確認を

Power BI Studio は組織の Power BI テナントに接続します。サインインと権限付与が必要になるため、利用可否を社内で確認してから使ってください。一方、TMDL拡張は通信を一切しないので、ローカル編集だけなら単独で安全に使えます。

1-2 PBIP の構造を先に理解する

Power BI をテキストで管理する形式（PBIP）は、実際には次のように分かれています。TMDLで編集するのは .SemanticModel の中だけです。

litho-overlay-dashboard の実際の構成
powerbi/
├── litho-overlay.pbip                   ← 全体をまとめる入口ファイル
├── litho-overlay.SemanticModel/         ← ★ここがTMDLの領域（データモデル）
│   ├── definition.pbism
│   └── definition/
│       ├── model.tmdl                   ← モデル全体の設定・テーブル参照
│       ├── relationships.tmdl           ← リレーション定義
│       ├── expressions.tmdl             ← 共有パラメーター・M式
│       ├── database.tmdl
│       └── tables/
│           ├── Measurements.tmdl        ← テーブル1つにつき1ファイル
│           ├── ShotCorrections.tmdl
│           ├── DimLot.tmdl
│           ├── DimWafer.tmdl
│           ├── Calendar.tmdl
│           └── Parameters.tmdl
├── litho-overlay.Report/                ← 見た目（PBIR形式・JSON）。TMDLではない
└── theme/litho-light-theme.json

⚠️よくある勘違い

TMDL が扱うのはデータモデルだけです。グラフの配置や色などのレポート側は .Report フォルダの JSON（PBIR形式）で、TMDL拡張の対象外です。「TMDLを直せば見た目も変わる」わけではありません。

TMDL 2. TMDL拡張の使い方 v1.6.5

2-1 この拡張がすること・しないこと

✅ してくれること❌ しないこと
  • .tmdl / .tmd の構文を色分け
  • キーワードの入力補完
  • DAX式の整形
  • フォルダ全体をまたいだ構文チェック（要設定）
  • サーバーへの接続・発行（Power BI Studio の担当）
  • モデルの意味的な妥当性チェック
  • コマンドの提供（0個。設定と色分けだけ）

つまり「TMDLを安全に手書きするための下地」です。入れるだけで効き、操作を覚える必要はありません。

2-2 設定6項目と推奨値

TMDL拡張の全設定
設定キー既定推奨理由
tmdlLanguageExtension.indentationStyleTabsTabs のまま 実際のリポジトリの全TMDLファイルがタブで統一されている（スペース行 0件）。ここを変えると既存ファイルと混在して事故になる
tmdlLanguageExtension.workspaceLevelParsingDisableEnable 既定ではファイル単位でしか見ない。有効にすると relationships.tmdl が参照する列名の誤りなど、ファイルをまたいだ矛盾に気づける
tmdlLanguageExtension.daxFormatterEnableEnable のままメジャーのDAXを整形できる
tmdlLanguageExtension.casingStyleCamelCamel のまま補完時の大文字小文字の扱い
tmdlLanguageExtension.newlineStyleDefaultDefault のまま改行コード。Gitの差分を無用に増やさないため既定推奨
tmdlLanguageExtension.powerquery.general.localeen-USen-US のままM式の解釈ロケール。モデルの culture: ja-JP とは別物なので変更不要

2-3 TMDLファイルの読み方

TMDLはインデントで階層を表す形式です。「何が何にぶら下がっているか」だけ分かれば読めます。

model.tmdl（実物・抜粋）
model Model
	culture: ja-JP
	defaultPowerBIDataSourceVersion: powerBI_V3
	sourceQueryCulture: ja-JP

	annotation __PBI_TimeIntelligenceEnabled = 0

ref table Measurements
ref table ShotCorrections
ref table DimLot
ref table DimWafer
ref table Calendar

ref table は「このテーブルは tables/ の別ファイルに定義がある」という参照です。テーブルを追加するときはファイルを作るだけでなく、ここに1行足す必要があります。忘れるとモデルに載りません。

2-4 実物で読み解く：DimWafer.tmdl

tables/DimWafer.tmdl（実物・全文。タブを見やすく空白表示にしています）
table DimWafer

    column WaferNo
        dataType: int64
        summarizeBy: none
        sourceColumn: WaferNo
        annotation SummarizationSetBy = Automatic

    partition DimWafer = m
        mode: import
        source =
                let
                    Source = Csv.Document(File.Contents(DataFolder & "measurements.csv"), [Delimiter=",", Encoding=65001, QuoteStyle=QuoteStyle.Csv]),
                    Promoted = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
                    Selected = Table.SelectColumns(Promoted, {"WaferNo"}),
                    Grouped = Table.Distinct(Selected),
                    Typed = Table.TransformColumnTypes(Grouped, {{"WaferNo", Int64.Type}})
                in
                    Typed

各行の意味
記述意味
table DimWaferテーブル名の宣言。ここが最上位
column WaferNo列の宣言。以下のインデントがこの列の属性
dataType: int64データ型
summarizeBy: none既定で合計などを取らない（IDや番号の列では必須級の設定）
sourceColumn: WaferNo取り込み元の列名。計算列ではなく実データの列であることを示す
partition DimWafer = mデータの取得方法。= m は Power Query（M言語）で取り込むという意味
mode: import取り込み方式（Import／DirectQuery の別）
source = let … in …実際のM式。CSVを読み、列を選び、重複を除き、型を付けている

2-5 編集するときの3つの鉄則

  1. インデントは既存ファイルに完全に合わせる
    このリポジトリは全ファイルがタブです。スペースを混ぜると読み込みに失敗します。エディタの表示だけでは見分けにくいので、既存行をコピーして書き換えるのが安全です。
  2. テーブルを足したら model.tmdl に ref table を足す
    ファイルを作っただけではモデルに含まれません。
  3. 1テーブル＝1ファイルを崩さない
    tables/ の構成はツール側の前提です。まとめたり分割したりしないでください。

Power BI Studio 3. Power BI Studio の使い方 v2.11.1

3-1 初期設定とサインイン

  1. サイドバーの Power BI アイコンを開く
    初回はサインインを求められます。組織アカウントで認証します。
  2. ワークスペースが多い場合は絞り込む
    設定 powerbi.workspaceFilter に正規表現を入れると、一覧に出すワークスペースを限定できます。
  3. TMDL機能を使う場合は追加設定
    powerbi.TMDL.enabled は既定で有効です。認証を VS Code 側に覚えさせたい場合のみ powerbi.TMDL.clientId を設定します（未設定でも毎回認証すれば使えます）。
  4. 更新の監視間隔を調整する
    powerbi.datasetRefreshCheckInterval は既定60秒。不要なら 0 で自動チェックを止められます。
⚠️powerbi.cloud は触らない

既定の GlobalCloud のままにしてください。これを変えるのは、政府向けなど特殊なクラウドに接続する場合だけです。

3-7 TMDL Proxy と、つまずいたときの見方

TMDL機能を初めて使うと、VS Code のターミナルに TMDL Proxy というプロセスが自動で立ち上がります。これは異常ではありません。Power BI のTMDLライブラリが .NET製で、VS Code（JavaScript）から直接呼べないため、間に立つ補助プログラムです。

よくある困りごと
症状原因対処
TMDL関連の操作が動かない.NET Runtime が見つからないこの環境は 10.0.11 が入っているので通常は問題なし。Ensure TMDL Proxy で起動を確認する
エラーの詳細が分からない—TMDL Proxy のターミナルがログになっています。ここに個々の要求と結果が出る
毎回認証を求められる認証をプロキシ側が担当しているためpowerbi.TMDL.clientId にAADアプリのIDを設定すると、VS Codeが資格情報を保持する
ワークスペースが一覧に出ない権限不足、またはフィルタAPI権限（Workspace.Read.All 等）と powerbi.workspaceFilter を確認
Publish が失敗するXMLA書き込みは Premium / PPU / Fabric 容量が必要共有容量のワークスペースでは発行できない。容量を確認する

4. 開発手順の2パターン

この2拡張の組み合わせ方には2通りあります。どちらか一方ではなく、目的で使い分けます。

パターンA：ローカルPBIPをGitで管理する（現行の進め方）

  1. ブランチを切る（例：feat/vertica-directquery）
  2. VS Code で .tmdl を編集する — TMDL拡張の色分けと補完が効く。既存ファイルのインデントに合わせる
  3. Power BI Studio の Validate TMDL で検証する — Macのまま構文の妥当性を確認できる
  4. コミットしてPRを出す — 差分がテキストなので、意図しないリレーション変更などをレビューで発見できる
  5. Windows実機の Power BI Desktop で開いて確認する — 描画やDesktop固有の挙動はMacでは検証できない
  6. マージする
✅この形の利点

モデル定義の変更履歴がGitに残り、PRでレビューできます。既存の開発フロー（ブランチ→PR→確認→マージ）にそのまま乗ります。

パターンB：サービス上のモデルを直接編集する（Macから完結）

  1. Workspaces ビューでデータセットを右クリック → Edit TMDL
  2. 編集する
  3. Validate TMDL で検証する
  4. Publish TMDL で反映する
  5. Save TMDL locally でローカルへ保存し、Gitへコミットする（履歴を残すため）
⚠️パターンBの注意

直接発行するため、手順5を省くとGitに履歴が残りません。また本番ワークスペースで実行すると即座に反映されます。まず開発用ワークスペースで試すか、事前に Backup を取ってください。

使い分けの目安
やりたいこと選ぶパターン理由
モデルを本格的に改修するAレビューと履歴が必要
本番の設定を少し直したいBダウンロード不要で速い。ただし後でGitへ保存する
既存モデルの中身を調べたいBEdit TMDL で開くだけ。編集せず閉じれば影響なし
DAXメジャーを試したいBノートブックの %dax が速い
他ワークスペースへモデルを複製したいBpbixの上げ下げ不要で、Validate → Publish でコピーできる

5. このプロジェクトで既に踏んだ地雷と回避策

過去に litho-overlay-dashboard で実際に発生し、Windows実機で初めて発覚した問題です。同じ形の編集をする前に必ず確認してください。

🛑地雷1：計算テーブルの列にリレーションを張らない

手書きの計算テーブル（CALENDAR() など）が作る列をリレーションの相手にすると、Windows の Power BI Desktop で「リレーションシップ … は無効な列IDを使用しています」となりファイルが開けなくなります。

回避策：リレーションに参加するディメンション（日付テーブル等）は、partition X = m の取り込み（M）テーブルで作り、列は通常の sourceColumn にします。実際に Calendar.tmdl は List.Dates を使ったMテーブルで作り直しています。なお、リレーションを持たない設定用の計算テーブル（Parameters の DATATABLE）は問題ありませんでした。

🛑地雷2：自動の日付/時刻（LocalDateTable）

日付列があり「自動の日付/時刻」が既定でオンだと、Windows の Desktop が開いた瞬間に LocalDateTable_<guid> を自動生成し、エラーで開けなくなります。リポジトリ側に該当ファイルが無くても、開いた時点で生成されて壊れるのが厄介な点です。

回避策：model.tmdl に次の注釈を入れて自動生成を止めます。専用のCalendarテーブルがあれば自動日付は不要です。

	annotation __PBI_TimeIntelligenceEnabled = 0

⚠️地雷3：Mac では描画とDesktop固有の挙動を検証できない

TMDLの構文チェックは Validate TMDL でMacからできますが、Desktopで開いたときの挙動までは分かりません。上の2つの地雷はどちらも構文的には正しく、実機で初めて発覚しました。

回避策：公式スキーマや公式サンプル、既に動いている実ファイルで裏を取る。可能なら tests/ に自動テストを追加して再発を防ぐ。モデル変更を含むPRは、マージ前にWindows実機での確認を挟む。

⚠️地雷4：資格情報をリポジトリに置かない

DirectQuery化で接続先を扱う際、サーバー名やデータベース名はパラメーターとして持てますが、資格情報はリポジトリに含めません。Power BI Desktop またはオンプレミスデータゲートウェイ側で設定します。Power BI Studio の Update Parameters は接続先の切り替えには使えますが、認証情報の保管場所ではありません。

6. 設定まとめ（コピペ用）

コマンドパレットで Preferences: Open User Settings (JSON) を開き、いちばん外側の { } の中に貼り付けてください。

  // ===== TMDL 言語拡張 =====
  // インデントはタブ。既存ファイルが全てタブなので変更しない
  "tmdlLanguageExtension.indentationStyle": "Tabs",
  // ファイルをまたいだ整合性チェックを有効化（既定はDisable）
  "tmdlLanguageExtension.workspaceLevelParsing": "Enable",

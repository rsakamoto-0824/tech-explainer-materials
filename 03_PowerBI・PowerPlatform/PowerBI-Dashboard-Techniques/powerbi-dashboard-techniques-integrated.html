三者一致の黄金ルール7箇条

3つのソースすべてが、表現を変えながら同じことを言っていました。これが Power BI ダッシュボード作成の核心です。

① グラフより先に土台（整形→モデリング）を固める ★ 三者一致

データの品質とモデル構造がダッシュボードの信頼性を決める。ビジュアルは最後。

② スタースキーマ＋日付テーブルが基本形 ★ 三者一致

ファクト（数値）とディメンション（切り口）を分離し、専用のカレンダーテーブルを必ず用意する。

③ 計算は「計算列」より「メジャー」 ★ 三者一致

メジャーは軽く・再利用でき・速い。計算列の多用はモデル肥大化のもと。

④ 1画面・1ストーリー、重要KPIは左上 ★ 三者一致

スクロールさせない。視線の流れ（左上→右下）に沿って概要→詳細に配置する。

⑤ 比較は棒グラフ。円・3Dの多用を避ける ★ 三者一致

人は長さの比較が最も正確にできる。円グラフはカテゴリ8個未満の構成比のみ。

⑥ 配色・フォントはテーマで統一し、色数を絞る ★ 三者一致

基本＋アクセントの2〜3色。JSONテーマファイルで組織的に統一するのが理想。

⑦ 詳細はページに詰め込まず、ドリル/ツールチップへ逃がす ★ 三者一致

ビジュアル数を絞ることは見やすさと表示速度の両方に効く。

4STEP3：データモデリング（スタースキーマ）

黄金ルール②の具体化。Power BIの実力はここで決まります。

スタースキーマの構造 ★ 三者一致

テーブル持つ情報例
ファクト（中心）数値・実績（集計対象）売上、利益、注文数
ディメンション（周辺）切り口となる属性商品・顧客・店舗・日付マスタ
  • リレーションは「多対一・単方向」が基本。双方向はループと誤集計のもと 日本語動画公式
  • 1つのテーブルにファクトとディメンションの役割を混在させない 日本語動画
  • モデルを使いやすく：分かりやすい命名・不要列の非表示・階層作成・既定書式の設定 公式

日付（カレンダー）テーブルは必須 ★ 三者一致

「良いカレンダーディメンションはあらゆるモデルの中核」英語動画。前年比・累計を正しく計算する前提条件です。

// CALENDARAUTO で日付範囲を自動生成し、属性列を追加
Calendar =
ADDCOLUMNS(
    CALENDARAUTO(),
    "Year",    FORMAT([Date], "yyyy"),
    "Month",   FORMAT([Date], "MMM"),
    "Quarter", "Q" & QUARTER([Date])
)

5STEP4：DAXとメジャー 統合版

3ソースの実例をまとめた「実務で使うDAXパターン集」です。

大原則 ★ 三者一致

  • 迷ったらメジャー。計算列はどうしても行単位の列が要るときだけ
  • 複雑な式は中間メジャーに分割して積み上げる（[売上]→[前年売上]→[前年比]）
  • ビジュアル内のインライン式でなく、名前付きメジャーで定義（再利用可能・テスト可能・高速）英語動画

パターン① 基本集計と安全な割り算 日本語動画

売上合計 = SUM(売上[金額])
ユーザー数 = DISTINCTCOUNT(アクセス[ユーザーID])

// DIVIDE は0除算エラーを防ぐ
達成率 = DIVIDE([売上合計], [目標値])

パターン② 条件付き集計（CALCULATE） 日本語動画英語動画

2023年売上 = CALCULATE(
    SUM(売上[金額]),
    売上[年] = 2023
)

パターン③ 前年比・累計（時間インテリジェンス） ★ 三者一致

// 前年同期（DATEADDが最も汎用的 — 英語動画の定番）
前年売上 = CALCULATE( [売上合計], DATEADD('Calendar'[Date], -1, YEAR) )

// 年初来累計
売上累計YTD = CALCULATE( [売上合計], DATESYTD('Calendar'[Date]) )

パターン④ VAR/RETURN で読みやすく 英語動画

前年比成長率 =
VAR CurrentRevenue = [売上合計]
VAR PriorRevenue   = [前年売上]
RETURN
    DIVIDE(CurrentRevenue - PriorRevenue, PriorRevenue)

パターン⑤ SWITCH で動的切替 英語動画

切断テーブル＋SWITCHで、売上／コスト／粗利や月次／YTDをボタン1つで切り替え。メジャーの重複作成を防ぐ英語圏の人気テクニックです。

Selected KPI =
SWITCH( SELECTEDVALUE(KpiSelector[Id]),
    1, [Revenue],
    2, [Cost],
    3, [Gross Profit]
)
💡 ビジュアル計算という近道もある 公式

累計・移動平均・構成比・順位などは、公式のビジュアル計算（visual calculations）を使えば、フィルター文脈を深く理解しなくてもビジュアル上で直接作れます。

  • スケールが極端に違うメジャーを同じ軸に混在（必要なら第2軸）

  3. 書式設定で色・フォント・％表示を調整し、前週比などの増減を添える

7STEP6：デザイン原則 統合版

黄金ルール④⑤⑥の実践編。三者の知見を「構成→配置→配色→文字→仕上げ」の順に統合しました。

構成 ★ 三者一致

  • 1画面・1ストーリー。スクロールバーを出さない
  • 必須でない情報は削る。詳細は別ページ・ドリルへ
  • 全体俯瞰 → セグメント別 → 個別データの順でストーリーを作る

配置 ★ 三者一致

  • 重要KPIを左上に。視線は左上→右下へ流れる
  • 同じ種類の情報はグルーピングし、適度な余白で区切る 日本語動画
  • 12カラムグリッドで設計し、Align／Distribute／Snap to grid でピクセル単位で揃える 英語動画

配色・文字 ★ 三者一致

  • 基本色＋アクセント2〜3色。同じ意味には同じ色
  • JSONテーマファイルで色・フォント・既定値を組織で統一 英語動画公式
  • フォントのサイズ・種類を統一（バラつくと目がちらつく）日本語動画
  • 大きな数値は3〜4桁に丸める（「3,400,000」より「340万」）公式

仕上げ 公式

  • アクセシビリティ：説明的タイトル・代替テキスト（alt text）・論理的なタブ順序・色だけに頼らない
  • モバイルレイアウトは専用エディタで別途設計し、重要ビジュアルだけを縦に積む 英語動画公式
  • 条件付き書式で状態を色で示す（ヒートマップ・アイコン）

9Deneb と「標準 vs カスタム」の使い分け

標準で足りないときの切り札。公式ドキュメント版レポートの核心部です。公式

Denebとは

Microsoft認定のカスタムビジュアル。Vega / Vega-Liteという宣言的JSONで独自の可視化を作れます。R/Pythonビジュアルと比べて ①外部依存なし ②Power BIクライアント内で描画するため速い ③クロスフィルター等のPower BI連携が可能、という利点があります。

最小の作成手順

  1. AppSourceからDenebを追加し、キャンバスに配置
  2. Valuesロールに列とメジャーを入れる（自動で内部データセットdatasetに結び付く）
  3. Edit → Vega-Liteテンプレートを選択 → 仕様（JSON）が生成される
{
  "data": { "name": "dataset" },   // ← Power BIのデータに接続（必須）
  "mark": "bar",
  "encoding": {
    "y": { "field": "City", "type": "nominal" },
    "x": { "field": "Mean Temperature", "type": "quantitative" }
  }
}

フィールドは表示名で参照し、. [ ]等の特殊文字は自動でアンダースコアに置換される点に注意（「データが出ない」ときの第一チェックポイント）。

使い分けの判断フロー

状況選択
棒・折れ線・カード等の定番で足りる標準ビジュアル（速い・保守が楽）
条件付き書式・分析ペイン・スモールマルチプルで足りる標準の高度機能
標準では表現できない独自の図が必要Deneb（Vega-Liteから着手）
📐 社内ルールとの対応

「まず標準機能 → 不足ならDenebを最優先で検討」という当社Power BI開発ルールは、この公式の考え方に沿ったものです。Denebの仕様（Vega-Lite定義）はJSONテキストとしてGitHubで差分管理します。

10パフォーマンス最適化と運用・ガバナンス

「遅くて使われない」「守りが甘い」を防ぐ横断ルールです。

スピードの数値目標 英語動画

  • 3秒以内のロードを目標に（5秒超で企業ユーザーは離脱）
  • 1ページのビジュアルは8個以下を目安に絞る

速くするテクニック ★ 三者一致

  • 不要な列・テーブルを取り込まない（データ削減が最大の高速化）
  • Top Nフィルターで表の表示件数に上限を設ける（例：10,000件）公式
  • 計算列よりメジャー。双方向リレーションを避ける
  • カスタムビジュアルは性能を実測してから本番投入 公式
  • ダッシュボードのタイルはキャッシュされ速い——よく使うビジュアルをピン留めして「最初の入口」にする 公式

運用・ガバナンス 英語動画公式

  • 行レベルセキュリティ（RLS）を本番に適用。USERPRINCIPALNAME()で動的制御も可能。ただし動的RLSはユーザー単位キャッシュになる性能影響に注意
  • 更新は業務時間外（深夜〜早朝）にスケジュール。社内DBはオンプレミスデータゲートウェイ経由
  • JSONテーマ・命名規則・Git等でのバージョン管理をチーム標準に
⚠ 機密データ・社外公開は要相談

個人情報・会員情報など漏れると致命的なデータを扱う場合や社外公開の判断が必要な場合は、自己判断で進めず社内のエンジニア／管理者に相談してください。アクセス権限と公開範囲は公開前に必ず確認しましょう。

11統合チェックリスト（公開前の最終点検）

3本のレポートのチェックリストを統合・重複排除した決定版です。

準備・設計

  • 答えるべき「3〜5の問い」を書き出したか
  • 閲覧者（経営層／現場）と閲覧デバイスを決めたか

データ・モデル

  • 不要な列・行を削除し、データ型を正しく設定したか
  • スタースキーマ（多対一・単方向）になっているか
  • 日付テーブルを用意し、ファクトと関連付けたか
  • 命名・非表示・階層・既定書式でモデルを使いやすくしたか

計算（DAX）

  • 集計は計算列でなく名前付きメジャーで作ったか
  • 割り算はDIVIDEで0除算対策をしたか
  • 複雑な式はVAR/RETURNや中間メジャーに分割したか
  • 前年比・累計が正しい数字を返すか確認したか

ビジュアル・デザイン

  • 重要KPIを左上、1画面・1ストーリーでスクロールなしか
  • 比較は棒グラフ、3D・円グラフの多用を避けたか
  • グリッドで整列し、テーマで色・フォントを統一したか
  • 数値を丸め、alt text等のアクセシビリティに配慮したか
  • モバイルレイアウトを別途作成したか

操作性

  • スライサー／ドリルスルー（＋戻るボタン）が意図通り動くか
  • ブックマークやツールチップページで詳細を逃がしたか

パフォーマンス・運用

  • 3秒以内ロード・1ページ8ビジュアル以下を満たすか
  • Top Nフィルターで表示件数を抑えたか
  • RLS・共有範囲・機密情報の扱いを確認したか

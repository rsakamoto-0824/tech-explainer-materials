Power BI ダッシュボード作成技術

📅 作成日：2026年6月24日
PART AMicrosoft 公式ドキュメント編

1公式：ビジュアル（visuals）の全体像

公式によると、ビジュアルはレポートの「構成要素（building blocks）」。セマンティックモデルとDAX計算を“意味のある洞察”に変換します。用途別の公式分類を押さえましょう。

用途別カテゴリ（公式分類）

カテゴリ 主なビジュアル 得意なこと
比較・推移 横棒/縦棒、折れ線、面、コンボ、リボン、ウォーターフォール カテゴリ比較・時系列トレンド・増減の積み上げ
全体に対する割合 円/ドーナツ、ツリーマップ、じょうごグラフ 構成比・階層的な割合・段階的プロセス
分布・関係 散布図、バブル、ドットプロット 2変数の相関・クラスター発見
明細表示 テーブル、マトリックス 正確な値の確認・多次元の集計とドリル
地理 各種マップ 地理・空間データの表示
重要数値・進捗 カード、KPI、ゲージ、目標(Goals) 単一指標の強調・目標への進捗
AI支援 分解ツリー、主要なインフルエンサー、スマートナラティブ、異常検出 要因分析・自然言語要約・外れ値検出
フィルター スライサー（ボタン/リスト/ドロップダウン/日付） キャンバス上での絞り込み
Microsoft Learn「Overview of visualizations」より ビジュアルは互いにクロスフィルター・クロスハイライトで連携し、完全にインタラクティブな体験を生む。さらに別ページ・別レポートへドリルスルーして詳細を探索できる。
📌 知っておくと差がつく公式ビジュアル
  • リボングラフ：期間ごとの「順位の変化」を、常に最上位を上にして見せる
  • 分解ツリー（Decomposition tree）：AIが次に見るべき次元を提案しながら任意の順で深掘り
  • スマートナラティブ：トレンドや要点を自動で文章化
  • R / Python ビジュアル：予測・統計など高度分析向け（※Denebとの比較は第7章）

2公式：適切なビジュアルの選び方

公式が示す選択の判断軸はシンプルです。

  • データ型：カテゴリ／数値／時系列／地理のどれか
  • 目的：値を比較する／トレンドを見る／関係を示す／進捗を追う
  • 閲覧者：どこまでの詳細が必要か
  • スペース：使える表示領域の広さ
Microsoft Learn「ダッシュボード設計のヒント」より 円・ドーナツ・ゲージなどの円形グラフは理想的ではない。値の比較には横棒・縦棒が優れている（人は値を横に並べて比較できるため）。3Dなど読み取りづらいビジュアルは避ける。

3公式：レポート/ダッシュボードのデザイン原則

公式ドキュメントが繰り返し説く、普遍的な設計原則です。

① ひと目でストーリーを語る

  • 各ページは「ひと目で1つのストーリー」を語る。スクロールバーを避ける
  • 最も重要な情報を目立たせ、清潔で雑然としないレイアウトに
  • カードビジュアルで重要数値を強調。コンテキスト（文脈）を必ず添える

② 読む順序に沿って配置

人は上から下・左から右に読む。最上位レベルのデータを左上に置き、右・下へ進むほど詳細に。数値は3〜4桁に丸め、千・百万単位で表示する（「3,400,000」より「340万」）。

③ アクセシビリティ（accessibility）に従う

Microsoft Learn より レポート設計ではアクセシビリティのベストプラクティスに従う。説明的なタイトル、ビジュアルの代替テキスト（alt text）、論理的なタブ順序を使い、誰もが使えるレポートにする。

④ モバイル最適化

モバイルレイアウトには重要かつ頻用するビジュアルだけを追加し、ヘッダーやデザインを簡素化して狭い画面に合わせる。

4公式：セマンティックモデルを使いやすくする

公式の最適化ガイドは「セマンティックモデル（semantic model）はすべてのレポートの基盤」と位置づけます。作り手が整えるべき項目です。

項目 公式が推奨すること
Names（命名） テーブル・列・メジャーに分かりやすい名前を。「Table1」より「Store Sales」
Descriptions（説明） 名前で足りない詳細は説明文に。何を含み、どう使うかを記す
Hide（非表示） IDなどレポートに不要な列は隠し、使ってほしいものだけ見せる
Hierarchies（階層） 年→月→日、カテゴリ→サブ→商品などの階層を作る
Measures（メジャー） 集計はメジャーで定義し、レポート間で一貫性を持たせる
Formats（書式） 桁区切り・小数桁・日付形式など既定の表示形式を設定（動的書式も可）
Data category（データ category） 列が「国」「Web URL」などであることを指定し、地図等で正しく扱う

さらに公式は、計算グループ（calculation groups）、フィールドパラメーター、What-ifパラメーター、グループ化／ビン分割なども状況に応じて評価するよう勧めています。

5公式：パフォーマンス最適化ガイド

公式は最適化を「データソース／データモデル／ビジュアル／環境」の4層で考えます。レポート作者が今日からできる要点を抜粋します。

① 最も限定的なフィルターを当てる

Microsoft Learn「Optimization guide」より ビジュアルが表示するデータが多いほど読み込みは遅くなる。例えば1億行のテーブルを無加工で置くのは典型的な失敗。「Top N」フィルターで表示件数を上限（例：10,000）に抑えれば、体験を損なわずメモリ使用が激減し性能が上がる。

② 1ページのビジュアル数を絞る

1ページのビジュアルは必要最小限に。詳細はドリルスルーページやレポートページツールチップで補えば、ページに詰め込まずに済む。テーブルは特にコストが高い点に注意。

③ カスタムビジュアルの性能を検証する

最適化が不十分なカスタムビジュアルはレポート全体の性能を落とす。導入前に必ず性能を確認する（Denebを使う際もこの観点が重要）。

④ ダッシュボードのキャッシュを活かす

ダッシュボードのタイルはキャッシュされ、レポートより安定して速い。よく使うビジュアルをダッシュボードにピン留めし、最初の入口にすると“第一の防衛線”になり、容量負荷も下がる。

⚠ RLSとキャッシュの注意

動的な行レベルセキュリティ（RLS）を使うと、タイルはユーザー単位でキャッシュされ、役割（role）ごとに更新クエリが発行されます。RLS適用時は性能影響を理解しておきましょう。

6公式：知っておきたい高度な分析機能

標準だけでも表現力を大きく上げられる、公式機能の数々です。

  • 条件付き書式（conditional formatting）：値・ルール・カラースケールで色を動的に。ヒートマップや状態表示に
  • レポートページツールチップ：ホバー時に1ページ丸ごとの詳細（関連グラフ・KPI）を表示
  • ビジュアル計算（visual calculations）：ビジュアル上で直接DAXを書き、累計・移動平均・構成比・順位をフィルター文脈を意識せず作成
  • 分析ペイン（Analytics pane）：定数線・平均線・最小/最大・中央値・パーセンタイル線、予測、異常検出を追加
  • スモールマルチプル（small multiples）：1つのビジュアルを地域別などに分割し、格子状に並べて比較
  • レポートテーマ（JSONテーマ）：色・フォント・背景を一括適用。JSONで書き出してチーム共有し、組織で統一
💡 まず標準機能を尽くす

ここまでの機能を組み合わせれば、多くの要件は標準ビジュアルだけで満たせます。「標準で足りるか」を先に検証してから、次章のDeneb（カスタム）を検討するのが公式・社内ルール双方に沿った進め方です。

PART BDeneb（カスタムビジュアル）編

7Deneb とは何か

標準ビジュアルで表現しきれない図を、宣言的なJSONで自由に作るための認定カスタムビジュアルです。

定義

DenebはMicrosoft Power BIの認定カスタムビジュアル（certified custom visual）で、Vega / Vega-Lite という宣言的JSON文法を使って独自のデータ可視化を作れます。「認定」はMicrosoftが品質・セキュリティ基準を満たすと認めた印です。

Vega と Vega-Lite の違い

Vega-Lite Vega
位置づけ 高水準・簡潔。少ない記述で標準的なグラフ 低水準・自由度最大。複雑/独自の表現向け
向いている人 まず使い始める人・一般的なグラフ 細部まで作り込みたい上級者

まずはVega-Liteから始めるのがおすすめ。足りなくなったらVegaへ、という順序が自然です。

R / Python ビジュアルに対するDenebの利点（公式）

Deneb公式「Introduction」より ① 外部依存なし：ライブラリが同梱され、ローカル環境やゲートウェイへの追加依存が不要。
② 描画が速い：Power BIクライアント内でレンダリングするため、外部委譲より高速になりやすい。
③ Webネイティブ：Power BIのインタラクティブ機能と統合できる。

publish to web・オンプレのReport Server・モバイルなど、Power BIレポートが動く場所ならどこでも動作するよう必要なライブラリが同梱されています。

8Deneb の導入と作成手順

公式の「Simple Worked Example」に沿った、最短の作成手順です。

インストール

AppSourceから入手するのが最も簡単で、最新版に保ちやすい方法です。ビジュアルの追加ダイアログで「Deneb」を検索して追加します。

作成ステップ（棒グラフの例）

  1. キャンバスにDenebビジュアルを配置する
  2. Valuesデータロールに、列（例 City）とメジャー（例 Mean Temperature）を追加
  3. ビジュアルのヘッダーからEditでビジュアルエディタを開く
  4. 「Create using… > Vega-Lite > テンプレート（例：Interactive bar chart / empty with Power BI theming）」を選択
  5. プレースホルダにフィールドを割り当て（City→カテゴリ軸、Mean Temperature→値軸）
  6. Createで初期JSON仕様（specification）が生成される

最小のVega-Lite仕様（イメージ）

{
  "$schema": "https://vega.github.io/schema/vega-lite/v5.json",
  "data": { "name": "dataset" },   // ← Power BIのデータに接続
  "mark": "bar",
  "encoding": {
    "y": { "field": "City", "type": "nominal" },
    "x": { "field": "Mean Temperature", "type": "quantitative" }
  }
}

仕上げ（config で見た目を統一）

公式例では別枠の config JSONで、フォント（Segoe UI）、軸線・目盛りの除去、バーの角丸（10px）、バー色（#605E5C）、グリッド線の破線（[1, 5]）などを設定し、Power BIらしい見た目に整えています。

9Deneb の dataset の仕組み

DenebでPower BIのデータを扱う心臓部です。ここを理解すれば自由に図が作れます。

自動バインド

ビジュアルのValuesデータロールに入れたデータは、Vega/Vega-Lite内の dataset という名前の内部データセットに自動的に結び付きます。列・メジャーの増減やフィルターによる行数の変化に応じて動的に更新されます。

仕様での参照方法

// Vega-Lite
"data": { "name": "dataset" }

// Vega
"data": [ { "name": "dataset" } ]

フィールド名のルール（つまずきポイント）

  • 参照には、データモデルの内部名ではなくValuesロールに表示される表示名（display name）を使う
  • 各行は、全ディメンション・メジャーの値の組み合わせ（テーブルの行粒度）に対応
  • 問題になりやすい文字（. [ ] \ "）は自動でアンダースコアに置換。例：$ Sales.Current → $ Sales_Current
  • データはJSONのオブジェクト配列として渡され、各オブジェクトが1行
📌 「データが出ない」ときの第一チェック

多くの場合、"data": {"name": "dataset"} の記述漏れか、フィールド名の表記ゆれ（表示名・置換後の名前）が原因です。まずここを確認しましょう。

10Deneb × Power BI インタラクティブ機能

Denebの真価は「自由な見た目」と「Power BIらしい操作性」を両立できる点にあります。

公式は連携できる機能として次の5つを挙げています。

  • Tooltips（ツールチップ）：ホバー時の補足情報。Power BIのレポートページツールチップとも連携可能
  • Context menus（コンテキストメニュー）：右クリックメニュー
  • Cross-filtering（クロスフィルター＝選択）：Denebの要素をクリックして他ビジュアルを絞り込む
  • Advanced cross-filtering（高度なクロスフィルター）：より細かな選択制御
  • Cross-highlighting（クロスハイライト）：選択値を強調し、それ以外を薄く表示
Deneb公式「Simple Worked Example」より 公式の棒グラフ例では、2つのbarマークを重ねた layered view を使い、元の値を不透明度30%、ハイライト値（Mean Temperature__highlight）を重ねて表示。特別なフィールド __selected__ が不透明度のエンコードを通じてクロスフィルターを制御する。

つまり、テンプレートから作ればクロスフィルター/ハイライトが最初から組み込まれた状態で始められます。

11標準ビジュアル vs Deneb の使い分け

公式の考え方と社内ルールを合わせた、実務的な判断基準です。

判断フロー

状況 選ぶもの 理由
一般的な棒/折れ線/カード/マトリックス等で足りる 標準ビジュアル 速い・保守が楽・学習コスト最小
標準＋条件付き書式/分析ペイン/スモールマルチプルで足りる 標準の高度機能 カスタム導入前にまず尽くす
標準では表現できない独自図・細かな制御が必要 Deneb Vega/Vega-Liteで自由表現。認定・外部依存なし・高速
予測・統計など計算主体 R/Python も候補だがDeneb優先で検討 外部依存なし・描画が速いため（社内ルール）
📐 社内ルール：Vega-Lite定義はGitで差分管理

Denebを使う場合も、仕様（Vega/Vega-Lite定義）はGitHubで差分（テキスト)管理しやすい形で保存します。DenebのspecはJSONテキストなので、.jsonとして書き出せばレビュー・履歴管理が容易です。バイナリ中心で差分が見えない形だけで管理しないこと。

⚠ カスタムビジュアル採用時の確認

公式が警告するとおり、最適化不足のカスタムビジュアルはレポート全体を遅くします。Deneb採用時も表示件数を絞り（Top N）、性能を実測してから本番投入しましょう。

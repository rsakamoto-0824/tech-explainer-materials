C#の条件付きコンパイル 総合ガイド

#if と [Conditional] の仕組みから、 他言語との設計思想の違い、DLL配布で踏みやすい地雷、 そして同名アセンブリが1プロセスに二重ロードされたときの挙動までを1本にまとめた資料です。

作成日: 2026-09-05 対象: .NET Framework 4.x / .NET 5以降（.NET Core系） 想定読者: C#でDLLを作って配布する人

1. 3分でわかる要点

  • #if はビルド時に片方のコードを丸ごと捨てる仕組み。DLLには残った側しか入らない。
  • C#のプリプロセッサは値を持つマクロを持たない。C/C++の #define MAX 100 のような使い方はできない。
  • [Conditional("DEBUG")] は #if と似て非なるもの。 呼び出す側のビルド設定で有効/無効が決まる。DLL配布ではこの違いが決定的。
  • DLLのアイデンティティは「名前＋バージョン＋カルチャ＋公開キー」だけ。 どのシンボルでビルドしたかはアイデンティティに現れない。 つまり「同名・同バージョンなのに中身が違うDLL」が作れてしまう。
  • 同名DLLが別々のロードコンテキストに2つ乗ると、CLRはそれを別の型として扱う。 InvalidCastException: 型 'Foo' を型 'Foo' にキャストできません という一見矛盾したエラーはこれ。 static フィールドも2つに分裂する。

この4点が結びつくと、実務で一番厄介な事故が起きます。 「同名・同バージョン・中身違い（デバッグ版と製品版）のDLLが、同じプロセスに同時に載っている」という状態です。 アセンブリ名もバージョンも同じなので、ログを見ても気づけません。第9章でこの状態を詳しく扱います。

2. 条件付きコンパイルの基本

2.1 何をするものか

条件付きコンパイルとは、コンパイラがソースを読む段階で、条件に合わない部分を「無かったこと」にする機能です。 実行時の if 文とは根本的に違い、条件に合わなかったコードは IL（中間言語）にすら変換されず、生成されるDLL/EXEに一切含まれません。

最小の例
#define VERBOSE_LOG          // ← ファイルの一番先頭にしか書けない

using System;

class Sample
{
    public void Run()
    {
        Console.WriteLine("処理を開始します");

#if VERBOSE_LOG
        Console.WriteLine("[詳細] 内部状態をダンプしました");   // VERBOSE_LOG 定義時だけコンパイルされる
#elif MINIMAL_LOG
        Console.WriteLine("[簡易]");
#else
        // 何も出さない
#endif
    }
}

2.2 使える指令の一覧

指令役割書ける場所・制約
#define / #undef シンボルを定義／定義解除する ファイルの先頭のみ（using や実コードより前）。効果はそのファイル内だけ。値は持てない
#if / #elif / #else / #endif 条件でコード領域を取捨する どこでも可。式には ! && || == != () と true/false のみ
#error / #warning コンパイルエラー／警告を意図的に出す 「想定外の構成でビルドされた」ことを早期に潰すのに有効
#region / #endregion エディタ上の折りたたみ領域 コンパイル結果には影響しない
#pragma warning 警告の抑制／復帰 disable したら必ず restore で戻す
#nullable null許容参照型の文脈切り替え enable / disable / restore
#line エラー報告の行番号・ファイル名を差し替える コード生成ツール向け。手書きコードではまず使わない

C#には #include がありません。他のファイルで #define したシンボルは そのファイルの外には一切伝わりません。 プロジェクト全体で効かせたいシンボルは、必ずビルド設定（csproj）側で定義します（第3章）。

2.3 条件式の書き方

シンボルは「定義されている＝true」「されていない＝false」の真偽値としてのみ評価されます。 値の比較（#if VERSION > 3 のような書き方）はできません。

条件式の可否
#if DEBUG && !UNIT_TEST          // OK: 論理演算子は使える
#if (NET48 || NET8_0) && WINDOWS // OK: カッコによるグループ化も可
#if DEBUG == true                // OK（ただし冗長。ふつうは書かない）

#if VERSION > 3                  // NG: 大小比較は不可
#if defined(DEBUG)               // NG: C/C++の defined 演算子は存在しない
#define MAX_RETRY 3               // NG: 値付きマクロは作れない

定数を切り替えたい場合は、シンボルで const の定義そのものを切り替えます。

値を切り替えたいときの定石
internal static class Limits
{
#if STRESS_TEST
    public const int MaxRetryCount = 100;
#else
    public const int MaxRetryCount = 3;
#endif
}

3. シンボルはどこで定義されるか

条件付きコンパイルのトラブルの大半は、「そのシンボル、本当に定義されてる？」の確認漏れです。 定義経路は4つあります。

3.1 定義の4経路

経路書き方有効範囲
ソース内 #define FOO そのファイルのみ。しかもファイル先頭限定
プロジェクトファイル <DefineConstants> そのプロジェクトの全ソース。実務ではこれが主役
SDKの暗黙定義 （自動） ターゲットフレームワークとOSに応じて自動で付く
コマンドライン csc /define:FOO
dotnet build -p:DefineConstants=FOO		 そのビルド実行のみ。CIでの一時切り替えに使う
csproj — 追記形式にするのが安全
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFrameworks>net48;net8.0</TargetFrameworks>
  </PropertyGroup>

  <!-- 良い: 既存の DEBUG / TRACE を消さずに足す -->
  <PropertyGroup>
    <DefineConstants>$(DefineConstants);COMPANY_INTERNAL</DefineConstants>
  </PropertyGroup>

  <!-- 構成ごとに変える場合 -->
  <PropertyGroup Condition="'$(Configuration)' == 'Release'">
    <DefineConstants>$(DefineConstants);PRODUCTION</DefineConstants>
  </PropertyGroup>

</Project>

<DefineConstants>COMPANY_INTERNAL</DefineConstants> と $(DefineConstants) を付けずに書くと、 SDKが用意した DEBUG や TRACE がまるごと消えます。 Debug.WriteLine が急に効かなくなる原因の定番です。

3.2 SDKが自動で定義するシンボル

.NET SDK形式のプロジェクトでは、ターゲットフレームワークに応じたシンボルが自動で定義されます。 マルチターゲット（<TargetFrameworks>）でAPI差を吸収する際の主役です。

ターゲット自動定義されるシンボル（抜粋）
net48 NETFRAMEWORK, NET48, NET48_OR_GREATER, NET472_OR_GREATER …（下位すべて）
netstandard2.0 NETSTANDARD, NETSTANDARD2_0, NETSTANDARD2_0_OR_GREATER, NETSTANDARD1_6_OR_GREATER …
net8.0 NET, NET8_0, NET8_0_OR_GREATER, NET6_0_OR_GREATER …, NETCOREAPP, NETCOREAPP3_1_OR_GREATER
net8.0-windows 上記に加えて WINDOWS, WINDOWS7_0_OR_GREATER など（OS版の指定に応じる）
構成（Configuration） Debug: DEBUG と TRACE／Release: TRACE のみ

RELEASE というシンボルは自動定義されません。 Visual StudioでRelease構成を選んでいても #if RELEASE は常にfalseで、 中のコードは永遠にビルドされません。しかも警告も出ません。正しくは #if !DEBUG と書きます。

常にfalse。中身は死んでいる
#if RELEASE
    SendTelemetry();
#endif
DEBUGの否定で表現する
#if !DEBUG
    SendTelemetry();
#endif

「意図しない構成でビルドされていないか」を機械的に検出したいときは、#error が有効です。

想定外の組み合わせをビルド時に落とす
#if DEBUG && PRODUCTION
#error DEBUG と PRODUCTION を同時に定義することはできません。ビルド構成を確認してください。
#endif

#if !NETFRAMEWORK && !NET
#error 想定外のターゲットフレームワークです。
#endif

4. [Conditional]属性 — #ifとの決定的な違い

System.Diagnostics.ConditionalAttribute は、 条件付きコンパイルのもう一つの顔です。DLLを配布する立場では、こちらの理解のほうが重要になります。

#if はそのコードを書いた側のビルド設定で決まる。
[Conditional] はそのメソッドを呼ぶ側のビルド設定で決まる。

4.1 動作の仕組み

[Conditional("DEBUG")] が付いたメソッドは、 呼び出し側をコンパイルするときに DEBUG が定義されていなければ、その呼び出し文ごと消えます。 引数の評価も含めて消えます。一方、メソッド本体はDLLに残ります。消えるのは呼び出し側です。

ライブラリ側（MyLib.dll / Releaseビルド）
using System.Diagnostics;

public static class Diag
{
    [Conditional("DEBUG")]
    public static void Log(string message)
    {
        // このメソッド本体は Release ビルドの MyLib.dll にも「残る」
        Console.WriteLine($"[DIAG] {message}");
    }

    public static int Calc()
    {
#if DEBUG
        return 1;   // ← Release ビルドでは DLL に含まれない（消える側）
#else
        return 2;   // ← Release ビルドの MyLib.dll に焼き付く
#endif
    }
}
利用側アプリ（Debugビルド）— 同じ Release版 MyLib.dll を参照
Diag.Log(BuildExpensiveMessage());
// → 利用側が Debug ビルドなので、この呼び出しは生き残り、実際に出力される。
//   ライブラリが Release でビルドされていたかどうかは無関係。

int v = Diag.Calc();
// → 常に 2。ライブラリのビルド時に確定済みで、利用側の構成では変えられない。

Debug.WriteLine や Debug.Assert は [Conditional("DEBUG")]、Trace.WriteLine は [Conditional("TRACE")] で作られています。 「Releaseにしたら Debug.WriteLine が消える」のは、 .NETのDLLが差し替わるからではなく、あなたのコードのコンパイル時に呼び出しが削除されるからです。

4.2 引数が評価されないという副作用

呼び出しが消えるということは、引数の式も実行されないということです。 引数に副作用を書くと、構成によって挙動が変わるバグになります。

Releaseでは Remove が実行されない
Debug.Assert(list.Remove(item));
Debug.Assert(++counter < Max);
副作用は外に出す
bool removed = list.Remove(item);
Debug.Assert(removed);

counter++;
Debug.Assert(counter < Max);

4.3 [Conditional]を付けられる条件

「呼び出しを丸ごと消す」という性質上、消しても意味が通る形にしか付けられません。

制約理由違反時のエラー
戻り値は void のみ呼び出しを消したら戻り値を作れないCS0578
out パラメータ不可消したら未代入変数が残るCS0685
override メソッド不可基底の宣言で決まるべきものだからCS0243
インターフェースのメンバーに付けられない／インターフェース実装にも付けられないインターフェース越しの呼び出しは実行時に解決されるため消しようがないCS0582 / CS0629
コンストラクター、デストラクター、演算子、明示的実装は不可同上CS0577

インターフェース越しの呼び出しでは効きません。 ILogger.Log のようにインターフェース経由で呼ぶ設計にしていると、 [Conditional] による削除は一切働きません。静的メソッドへの直接呼び出しが前提の機能です。

4.4 属性クラスに付けるパターン

[Conditional] は属性クラスにも付けられます。 シンボルが定義されていない場合、その属性はメタデータに書き込まれません。 デバッグ専用のマーカー属性を製品版から消す用途に使えます。

DEBUGビルドのときだけメタデータに残る属性
[Conditional("DEBUG")]
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method)]
public sealed class InternalOnlyAttribute : Attribute { }

5. 言語仕様レベルの落とし穴

5.1 無効ブロックはコンパイルされない＝壊れていても気づけない

#if は字句（トークン）レベルで働きます。 条件が偽になった領域は構文解析も型チェックも参照解決も行われません。 その結果、無効側のコードが壊れたままビルドが通ってしまいます。

これは Release ビルドで通ってしまう
#if DEBUG
    // Release ビルドではこの行は一切検査されない。
    // 存在しないメソッドを呼んでいてもエラーにならず、
    // Debug ビルドに切り替えた瞬間に初めて壊れる。
    Logger.WriteVerboseDump(state, alreadyRenamedParameter);
#endif

これは単なる理屈ではなく、IDEのリファクタリングが無効ブロックに届かないという実害があります。 変数名の一括リネーム、メソッドのシグネチャ変更、参照の検索、静的解析、コードカバレッジ —— いずれも無効ブロックを素通りします。#if の中のコードは「腐る」前提で扱ってください。

対策: CIで全構成をビルドすることです。 Releaseだけでなく Debug も、マルチターゲットなら全TFMを毎回ビルドすれば、無効ブロックの腐敗を検出できます。

5.2 組み合わせが爆発する

独立したシンボルが N 個あると、理論上のビルド構成は 2N 通りになります。 5個で32通り、10個で1024通り。もちろん全部はテストされません。 実際にビルドし、テストする構成だけを定義するのが鉄則です。

シンボル数理論上の構成数現実
1（DEBUG のみ）2両方テストされる
382〜3構成しかテストしていないことが多い
6以上64以上「そのフラグ、まだ動く？」が誰にも分からない状態

5.3 ネストと巨大ブロック

読めない・追えない
#if NETFRAMEWORK
  #if DEBUG
    #if !UNIT_TEST
      ...200行...
    #endif
  #else
      ...150行...
  #endif
#endif
差分を1メソッドに閉じ込める
static string GetTempRoot()
{
#if NETFRAMEWORK
    return Path.GetTempPath();
#else
    return Path.Combine(
        Environment.GetFolderPath(
            Environment.SpecialFolder.LocalApplicationData),
        "tmp");
#endif
}

#if は「短く」「メソッド単位で」「1箇所に集約して」使うのが原則です。 差分が大きいなら、ファイルごと分ける方法（第7章）に切り替えます。

5.4 公開APIの形を #if で変えない

これはDLL配布に直結する最重要ルールなので、第8章で改めて扱います。 ひとことで言えば、publicなメンバーの有無・シグネチャ・フィールドの並びを #if で変えると、 ビルド構成によってDLLの「契約」そのものが変わってしまうということです。

6. 他言語との違い

「条件付きコンパイル」という言葉は多くの言語にありますが、 どの段階で・何の単位で切り替えるかが言語ごとに違います。 この違いを押さえると、C#の #if の性格がはっきりします。

6.1 早見表

言語主な仕組み処理の段階 値付きマクロ切り替えの単位無効側の構文チェック
C / C++ #if / #define（独立したプリプロセッサ） コンパイル前のテキスト処理 あり（関数形式も可） 任意のテキスト範囲。#include で伝播 されない
C# #if ＋ [Conditional] コンパイラ内部の字句解析 なし ファイル内の任意範囲。シンボルはファイル or プロジェクト単位 されない
Java 言語機能としてはなし。static final boolean の定数畳み込みが慣用 コンパイル時の最適化 なし if文の単位 される（普通のコードなので）
Rust #[cfg(...)] 属性、cfg!() マクロ、Cargo の feature パース後の構文木処理 featureは真偽値。値は env! 等で別途 構文要素（関数・モジュール・フィールド）単位 される（構文的に正しい必要あり）
Go ビルドタグ //go:build、ファイル名の _windows.go サフィックス ビルド対象ファイルの選択 なし ファイル単位のみ 選ばれなければ検査されない
Swift #if ＋ -D、実行時判定は #available コンパイル時（宣言・文の単位） なし 宣言や文の単位 C#より厳しく、部分的に検査される
Python なし。if sys.platform == ... の実行時分岐 実行時 — — される（構文エラーは常に検出）
TypeScript / JS バンドラの定数置換（process.env.NODE_ENV 等）＋ tree shaking バンドル時 あり（テキスト置換） 式の単位 される（型チェックは全体に及ぶ）
MATLAB なし。ispc / ismac 等の実行時分岐 実行時 — — される

6.2 C/C++との違い — ここが一番誤解される

C#の # 指令は「プリプロセッサ」と呼ばれますが、 C/C++のような独立した前処理プログラムは存在しません。 コンパイラが字句解析するときに一体で処理されるだけです。結果として、次の機能がまるごと存在しません。

C/C++ にあるものC# での扱いC# での代替
#define PI 3.14（値付き） 存在しない const double Pi = 3.14;
#define MAX(a,b) ...（関数形式マクロ） 存在しない ジェネリックメソッド、[MethodImpl(MethodImplOptions.AggressiveInlining)]
#include "header.h" 存在しない アセンブリ参照 <ProjectReference> / <PackageReference>、global using
インクルードガード #ifndef X_H 不要（そもそもテキスト展開しない） —
defined(X) 演算子 存在しない シンボル名をそのまま真偽値として書く
__FILE__ / __LINE__ 存在しない [CallerFilePath] / [CallerLineNumber]（コンパイラが引数に埋める）

C#が値付きマクロを持たないのは「意図的な制限」です。 マクロによる意味の書き換えを禁じることで、ソースコードの見た目と実際の意味を一致させることを優先しています。 C++から移ってきた人が最初に戸惑うポイントですが、 代替（const、ジェネリクス、[Caller*] 属性）が用意されています。

6.3 Rustとの違い — 字句 vs 構文木

Rustの #[cfg] は構文木の要素に付ける属性です。 条件が偽でも、そのコードはパースされる必要があります。 つまり構文エラーはちゃんと検出されます。C#の #if にはこの安全網がありません（第5.1節）。

C# — 無効側は検査されない
#if WINDOWS
    this is not valid csharp at all
#endif
// WINDOWS 未定義ならビルドは通ってしまう
Rust — 無効側もパースされる
#[cfg(target_os = "windows")]
fn platform_init() { /* ... */ }

// 構文が壊れていれば cfg が偽でもコンパイルエラー

※ 上の比較は「安全網の有無」を示すためのもので、良し悪しの対比ではありません（両側とも灰色にしています）。

6.4 Goとの違い — ファイル単位という割り切り

Goには #if がなく、ファイルごと切り替える方式に一本化されています。 store_windows.go と store_linux.go を置けば、 ビルド対象のファイルが自動で選ばれます。差分がファイル境界で明確になり、 「同じ関数の中に2つの実装が混ざる」ことが起きません。

C#でも同じ設計は再現できます。csprojで Compile 項目を条件付きにする方法です（第7.4節）。 差分が大きいときは #if より読みやすくなります。

6.5 Javaとの違い — 「機能がない」ことの意味

Javaには条件付きコンパイル構文がありません。代わりに static final boolean DEBUG = false; のような定数で if を書くと、 javacが定数畳み込みして到達不能ブロックを除去します。 C#の [Conditional] と発想は近いですが、 Javaのやり方はコードが普通のJavaなので構文・型チェックが常に効く点が違います。 C#でも同等のことを const bool で書けます。

C#でも「常に検査される分岐」は書ける
internal static class Features
{
#if DEBUG
    public const bool VerboseDiagnostics = true;
#else
    public const bool VerboseDiagnostics = false;
#endif
}

// 呼び出し側は普通のif。型チェックもリネームも効く。
// const が false ならコンパイラが到達不能コードとして除去する（CS0162 の警告付き）。
if (Features.VerboseDiagnostics)
{
    DumpInternalState();
}

#if のブロックを広範囲に散らすくらいなら、 #if は「const 1個の定義」だけに限定し、あとは普通の if で書く ほうが保守しやすくなります。IDEのリネームも静的解析もカバレッジも効きます。

7. #ifを使わない選択肢

#if が本当に必要な場面は、実は多くありません。 「そのAPIがそもそも存在しない」「そのプラットフォーム向けにコンパイルできない」場合に限られます。 それ以外は、より安全な手段があります。

7.1 判断の順序

Q1. 切り替えたい内容は、実行時に決めても間に合うか？

→ YES: 設定ファイル、環境変数、DI（依存性注入）、フィーチャーフラグで実行時に切り替える。
同じバイナリを全環境に配れるので、第8章・第9章の事故がまるごと消えます。これが第一候補です。

Q2. OSやランタイムの違いが理由か？

→ OperatingSystem.IsWindows() / RuntimeInformation.IsOSPlatform(...) を使う。
.NET 5以降の OperatingSystem.IsXxx() はJITが定数として畳み込み、不要な分岐を除去します。 さらにプラットフォーム互換性アナライザ（CA1416）が「このAPIはWindows専用」を静的に検査してくれます。

Q3. 対象フレームワークにそのAPIが存在しないのか？

→ ここで初めて #if NETFRAMEWORK 等の出番。差分は小さなメソッド1つに閉じ込める。

Q4. 差分がクラス丸ごと・数百行規模か？

→ #if ではなくファイルを分ける（7.4節）。

7.2 実行時判定（OS・ランタイム）

無効側が検査されない
#if WINDOWS
    RegistryHelper.Write(key, value);
#else
    FileHelper.Write(path, value);
#endif
両方が常に検査される
if (OperatingSystem.IsWindows())
    RegistryHelper.Write(key, value);
else
    FileHelper.Write(path, value);

ただし、net8.0（OS指定なし）ではWindows専用APIをそもそも参照できない場合があります。 「コンパイルが通らない」場合だけ #if に落とします。

7.3 フィーチャーフラグ／設定による切り替え

設定で切り替える（同一バイナリを全環境に配れる）
public sealed class DiagnosticsOptions
{
    public bool VerboseLogging { get; init; }
    public bool EnableInternalEndpoints { get; init; }
}

// appsettings.json / 環境変数 / DBなどから読む。
// 検証環境と本番で「同じDLL」を使いながら挙動だけ変えられる。

7.4 ファイルごと切り替える（Go方式）

差分が大きいときは、実装ファイルを分けてcsprojで選択します。 partial class と組み合わせると自然に書けます。

csproj — TFMごとに別ファイルをコンパイル
<ItemGroup>
  <!-- 既定の全ファイル取り込みから外す -->
  <Compile Remove="Platform\**\*.cs" />
</ItemGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'net48'">
  <Compile Include="Platform\FileStore.NetFramework.cs" />
</ItemGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'net8.0'">
  <Compile Include="Platform\FileStore.Net8.cs" />
</ItemGroup>
partial で共通部分と差分を分離
// FileStore.cs（共通・常にコンパイル）
public partial class FileStore
{
    public void Save(string name, byte[] data)
    {
        var root = GetRootPath();   // ← 実装は差分ファイル側
        File.WriteAllBytes(Path.Combine(root, name), data);
    }

    private partial string GetRootPath();
}

// FileStore.Net8.cs（net8.0 のときだけコンパイル）
public partial class FileStore
{
    private partial string GetRootPath()
        => Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData);
}

この方式の利点は、選ばれなかったファイルも普通のC#として書けることです。 エディタ上では対象TFMを切り替えれば、それぞれが正しく検査されます。 欠点は、共通部分と差分を跨いだ変更が2ファイルに散ることです。 差分が10行未満なら #if、それ以上ならファイル分割、が実用的な目安です。

8. DLLをデプロイするうえでの注意点

#if の結果はDLLに焼き付いてしまい、 しかもDLLのアイデンティティには現れません。 「見た目が同じで中身が違うDLL」を作れてしまうことが、デプロイ事故の根本原因です。

8.1 アセンブリのアイデンティティに含まれるもの

要素例アイデンティティに含まれるか
単純名（Simple Name）MyCompany.Core✅ 含まれる
アセンブリバージョン2.1.0.0✅ 含まれる

8.2 事故パターン1: Debugビルドが本番に混入する

Debugビルドは単に DEBUG シンボルが付くだけでなく、実行時特性も変わります。

観点DebugビルドReleaseビルド

配置済みDLLの構成を実行時に確認する

AssemblyConfiguration 属性はSDK形式プロジェクトが自動生成するため、 これを読めば「配置されているDLLがDebugかRelease」かを判定できます。

C# — 読み込み済みアセンブリのビルド構成を一覧する
using System;
using System.Linq;
using System.Reflection;

foreach (var asm in AppDomain.CurrentDomain.GetAssemblies()
                            .Where(a => !a.IsDynamic)
                            .OrderBy(a => a.GetName().Name))
{
    var config = asm.GetCustomAttribute<AssemblyConfigurationAttribute>()?.Configuration ?? "(不明)";
    var info   = asm.GetCustomAttribute<AssemblyInformationalVersionAttribute>()?.InformationalVersion ?? "-";

    Console.WriteLine($"{asm.GetName().Name,-40} {asm.GetName().Version} " +
                      $"構成={config,-8} 情報版={info}");
    Console.WriteLine($"    場所 : {asm.Location}");
    Console.WriteLine($"    MVID: {asm.ManifestModule.ModuleVersionId}");
}
PowerShell — 配置済みDLLをプロセス起動なしで調べる
# 対象フォルダのDLLの構成・バージョンを一覧
Get-ChildItem 'C:\inetpub\myapp\bin' -Filter *.dll | ForEach-Object {
    $a = [System.Reflection.Assembly]::ReflectionOnlyLoadFrom($_.FullName)
    [PSCustomObject]@{
        Name    = $a.GetName().Name
        Version = $a.GetName().Version
        Config  = ($a.GetCustomAttributesData() |
                   Where-Object { $_.AttributeType.Name -eq 'AssemblyConfigurationAttribute' }
                  ).ConstructorArguments.Value
        File    = $_.FullName
    }
} | Format-Table -AutoSize

ReflectionOnlyLoadFrom は .NET Framework 用です（Windows PowerShell 5.1 で動作）。 .NET Core / PowerShell 7 では System.Reflection.Metadata か、 ilspycmd・ILSpy などのツールを使います。

8.3 事故パターン2: #ifで公開APIの形が変わる

これが最も危険です。 publicメンバーの有無やシグネチャを #if で変えると、 「ビルド構成によってDLLの契約そのものが変わる」ことになります。 参照側はコンパイル時に見えたシグネチャで呼び出しコードを生成するため、 実行時に別構成のDLLが置かれると MissingMethodException や TypeLoadException で落ちます。 コンパイルは通り、テストも通り、本番だけで落ちます。

publicの契約が構成で変わる
public class Engine
{
    public void Run() { }

#if DEBUG
    // Debug版DLLにしか存在しない public メソッド
    public void DumpState() { }
#endif

#if DEBUG
    // 引数の数まで変わる最悪パターン
    public void Start(int id, bool verbose) { }
#else
    public void Start(int id) { }
#endif
}
契約は固定。中身だけ変える
public class Engine
{
    public void Run() { }

    // シグネチャは常に存在する
    public void DumpState()
    {
#if DEBUG
        WriteInternalState();
#endif
        // Release では何もしない
    }

    // 引数は常に同じ。挙動を実行時に切り替える
    public void Start(int id, bool verbose = false) { }
}

ルール: #if はメソッドの内側だけで使う。 public なメンバーの宣言そのものを囲まない。
どうしてもデバッグ専用のAPIが要る場合は、別アセンブリ（例: MyLib.Diagnostics.dll）に切り出し、 本番には配置しない。そちらのほうが安全で意図も明確です。

シリアライズ対象のクラスで #if によりフィールドを増減させるのも同種の事故です。 バイナリシリアライズやフィールド順に依存する相互運用（P/Invokeの構造体レイアウトなど）では、 構成が違うだけでデータが壊れます。

8.4 マルチターゲットとNuGetのフォルダ構造

#if NETFRAMEWORK / #if NET8_0_OR_GREATER によるマルチターゲットは、 最終的にNuGetパッケージ内の lib/<TFM>/ フォルダに落ちます。 同名のDLLがTFMの数だけ存在し、中身が全部違います。

NuGetパッケージの中身（同名DLLが複数ある）
MyCompany.Core.2.1.0.nupkg
├─ lib/
│   ├─ net48/
│   │    └─ MyCompany.Core.dll     ← NETFRAMEWORK 版（中身が違う）
│   ├─ netstandard2.0/
│   │    └─ MyCompany.Core.dll     ← NETSTANDARD 版（中身が違う）
│   └─ net8.0/
│        └─ MyCompany.Core.dll     ← NET8_0 版（中身が違う）
└─ MyCompany.Core.nuspec

# 復元時に、参照側のTFMに合う1つだけが選ばれて出力フォルダにコピーされる。

手コピー配布の危険: ビルド出力の bin\Release\net48\MyCompany.Core.dll を 「同じ名前だから」と .NET 8 アプリのフォルダに手動で置くと、TFM選択の仕組みが働きません。 運が良ければ BadImageFormatException や TypeLoadException で即死しますが、 運が悪いと一部のAPIだけ挙動が違う状態で動いてしまいます。 配布は必ずNuGetパッケージか、ビルド成果物一式（発行フォルダ）単位で行ってください。

8.5 ビルド警告 MSB3277 / MSB3243 を無視しない

「同名アセンブリの異なるバージョンが競合しています」という警告は、 第9章で扱う多重ロード問題のビルド時点での予告です。実務では最重要の警告の1つです。

見逃してはいけない警告
warning MSB3277: Found conflicts between different versions of
"Newtonsoft.Json" that could not be resolved.

warning MSB3243: No way to resolve conflict between
"MyCompany.Core, Version=2.1.0.0" and "MyCompany.Core, Version=2.0.0.0".

対策は、①依存バージョンを一本化する（Directory.Packages.props による中央管理）、 ②.NET Frameworkなら <AutoGenerateBindingRedirects>true</AutoGenerateBindingRedirects> を有効にして バインディングリダイレクトを生成する、の2つです。 「動いているから」と放置すると、第9章の症状に発展します。

8.6 「同名・同バージョン・中身違い」を作らない仕組み

① Build once, deploy many

検証環境と本番環境でビルドし直さない。CIで1回だけビルドした成果物を、そのまま全環境へ配る。 再ビルドする運用は「同名同バージョン別バイナリ」を量産します。

② 決定的ビルド（Deterministic Build）

SDK形式では既定で Deterministic=true。 CIでは <ContinuousIntegrationBuild>true</ContinuousIntegrationBuild> も設定します。 入力が同じなら出力バイト列も同じになるため、ハッシュ比較でバイナリの同一性を検証できるようになります。

③ バージョンにビルド情報を埋める

csproj — コミットハッシュを情報バージョンに刻む
<PropertyGroup>
  <Version>2.1.0</Version>
  <Deterministic>true</Deterministic>
  <ContinuousIntegrationBuild Condition="'$(CI)' == 'true'">true</ContinuousIntegrationBuild>
  <SourceRevisionId>$(GIT_COMMIT)</SourceRevisionId>
  <!-- → InformationalVersion が "2.1.0+9f60915" のようになる -->
</PropertyGroup>

④ デバッグシンボル（PDB）の扱い

Release配布でもPDBは有用です。<DebugType>portable</DebugType>（既定）でPDBを別ファイルとして生成し、 シンボルサーバやSourceLinkで管理します。embedded にすればDLLに埋め込めます（サイズ増）。 PDBの有無はコード生成に影響しません —「PDBを配ったからDebugビルド」ではありません。

9. 同名DLLが複数メモリ展開されるとどうなるか

.NETの型のアイデンティティは「アセンブリのアイデンティティ」だけでなく「どのロードコンテキストに載ったか」も含みます。 同じ MyLib.dll v1.0.0 が2つのコンテキストに載ると、 中の MyLib.Engine は2つの別々の型になります。 static フィールドも2組に分裂します。

9.1 前提: ロードコンテキストという概念

.NET Framework AppDomainと3つのバインディングコンテキスト

コンテキスト入る方法同名・同バージョンの扱い依存の解決
Load（既定） Assembly.Load(name)、通常の参照解決 1つに集約される（GAC → AppBase → PrivateBinPath の順に探索） 自動
LoadFrom Assembly.LoadFrom(path) 同じアイデンティティがLoadコンテキストに既にあればそちらが返る（指定パスは無視される） 同じディレクトリから自動解決
どのコンテキストでもない Assembly.LoadFile(path)、Assembly.Load(byte[]) パスごとに別インスタンスが作られる。同名同バージョンでも重複ロードされる 自動解決されない（AssemblyResolve の実装が必要）

.NET 5以降 AssemblyLoadContext（ALC）

.NET Core系では追加のAppDomainを作れません。代わりに AssemblyLoadContext が分離の単位になります。

  • Default ALC: deps.json と実行ディレクトリから解決。 同じ単純名のアセンブリは1つしか載りません。 2つ目を要求すると、既に読み込み済みのものが返ります。 バージョンが違う場合は上位バージョンへ自動ロールフォワードします（FrameworkのようなbindingRedirect設定は不要）。
  • 独自ALC: new MyPluginContext(...) を作れば、 同名・同バージョンのアセンブリを意図的に複数ロードできます。プラグイン分離の標準手法です。
  • Collectible ALC: isCollectible: true で作ると Unload() できます。 ただし、そのALCの型・インスタンスへの参照が1つでも残っていると解放されません。
  • Assembly.LoadFile(path) は .NET Core系では呼ぶたびに新しい無名ALCを作ります。 ループで呼ぶと重複ロードが積み上がります。

9.2 何が起きるか

1つのプロセス（同名DLLが2つ載っている状態）

Default ALC ／ Load コンテキスト

MyLib.dll Version = 1.0.0.0 C:\app\bin\MyLib.dll Releaseビルド

PluginContext ／ LoadFile

MyLib.dll Version = 1.0.0.0 C:\app\plugins\x\MyLib.dll Debugビルド

アセンブリ名もバージョンも同一。しかしCLRにとっては別アセンブリ・別型。

症状1: 同名の型なのにキャストできない

典型的な例外メッセージ（.NET Framework）
System.InvalidCastException:
  [A]MyLib.Engine を [B]MyLib.Engine にキャストできません。
  型 A は 'MyLib, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null' から
    コンテキスト 'LoadNeither'（場所 'C:\app\plugins\x\MyLib.dll'）に読み込まれています。
  型 B は 'MyLib, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null' から
    コンテキスト 'Default'（場所 'C:\app\bin\MyLib.dll'）に読み込まれています。

「型Aを型Aにキャストできない」という一見矛盾したメッセージが、多重ロードの決定的な証拠です。 同様に is / as が失敗し、 typeof(Engine) == instance.GetType() が false になります。

症状2: staticが分裂する

static フィールドはアセンブリのロード単位ごとに独立して確保されます。 シングルトン、キャッシュ、カウンタ、イベントの購読リスト、lock 用オブジェクトがすべて2組になります。

静かに壊れるパターン
public static class ConnectionPool
{
    private static readonly object Gate = new();
    private static Connection? _shared;

    public static Connection Get()
    {
        lock (Gate)                    // ← 2つのALCで Gate は別オブジェクト。排他が成立しない
        {
            return _shared ??= Connect(); // ← 「単一の」接続が2本張られる
        }
    }
}

この症状は例外にならないのが厄介です。 接続が2本になる、キャッシュが効かない、初期化が2回走る、イベントが片方にしか届かない、 設定変更が反映されない —— 症状が「なんとなくおかしい」の形で現れ、原因究明が長引きます。

症状3: 条件付きコンパイルとの合わせ技（本題）

2つの MyLib.dll v1.0.0 が、片方は DEBUG 定義あり、 片方はなしでビルドされていたとします。
アセンブリ名もバージョンも同じなので、ログにも例外メッセージにも差が出ません。 検証コードが走ったり走らなかったり、ログが出たり出なかったり、 Limits.MaxRetryCount が 3 だったり 100 だったりします。 「どちらのDLLがその処理を実行したか」を、ファイルパスとMVIDを出力するまで誰も特定できません。

症状4: メモリと初期化コストの二重化

  • ILとメタデータがロードコンテキストごとにマップされ、JITコードも別々に生成されます。
  • 型初期化子（static コンストラクター）が2回実行されます。 ここでファイル・ポート・COM登録・ハードウェアなどプロセス外の資源を掴んでいると、衝突します。
  • Collectible ALCでない限り、プロセス終了までアンロードされません。

症状5: ネイティブDLLは別のルールで動く

DllImport で呼ぶネイティブDLLは、OSの LoadLibrary で読み込まれ、 プロセス単位・モジュールパス単位で管理されます。 マネージド側が2つのALCに分かれていても、同じパスのネイティブDLLなら1つのモジュールを共有します。 つまりネイティブ側のグローバル状態は共有され、マネージド側の状態は分裂するという、 最も混乱しやすい組み合わせが発生します。 逆に、プラグインごとに別パスの同名ネイティブDLLを置くと、ネイティブ側も2重ロードされます。

9.3 どういうときに起きるか

状況起きる理由
プラグイン／アドイン型アプリ（Office VSTO、AutoCAD、Revit、Visual Studio拡張など） ホストが複数のアドインを1プロセスに読み込み、各アドインが自分のフォルダの共通ライブラリを LoadFrom / LoadFile する
自作プラグインローダー フォルダを走査して Assembly.LoadFile をループで呼ぶ実装
.NET FW GACとbinの二重配置 強い名前のアセンブリはGACが優先される。binに新しいDLLを置いても反映されない
IISの複数アプリケーション／ShadowCopy アプリケーションプールの構成や一時フォルダのコピーが絡む
ILMerge / ILRepack で埋め込んだライブラリ 埋め込み版と、外部に置かれた同名DLLが共存する
テストランナー 複数のテストアセンブリがそれぞれ別フォルダから依存を読み込む
手動での部分的なDLL差し替え 「このDLLだけ新しくすればいい」と1ファイルだけ上書きし、依存関係の整合が崩れる

9.4 プラグイン方式で「意図的に」分離する正しいやり方

多重ロードは事故とは限りません。プラグインごとに依存バージョンを分けたい場合は、 意図的にALCで分離するのが正解です。ただし1点だけ守るべき鉄則があります。

鉄則: ホストとプラグインが受け渡しする「契約アセンブリ（インターフェース定義）」だけは、 必ずホスト側のALCから1つだけ読み込ませる。
契約までプラグイン側でロードすると、IPlugin が2つの別型になり、 キャストできずにプラグインが1つも動きません。

.NET 5以降 — プラグイン用ALCの定石
using System.Reflection;
using System.Runtime.Loader;

internal sealed class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath)
        : base(name: Path.GetFileNameWithoutExtension(pluginPath), isCollectible: true)
    {
        // プラグインの .deps.json を読んで依存を解決する
        _resolver = new AssemblyDependencyResolver(pluginPath);
    }

    protected override Assembly? Load(AssemblyName name)
    {
        // ★重要★ 契約アセンブリは自分でロードせず、null を返して
        //         Default ALC（ホスト側）に解決させる
        if (name.Name == "MyApp.PluginContracts")
            return null;

        var path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }
}
プラグイン側csproj — 契約DLLを出力にコピーさせない
<ItemGroup>
  <!-- コンパイルには使うが、実行時のDLLはコピーしない -->
  <ProjectReference Include="..\MyApp.PluginContracts\MyApp.PluginContracts.csproj">
    <Private>false</Private>
    <ExcludeAssets>runtime</ExcludeAssets>
  </ProjectReference>
</ItemGroup>

契約アセンブリはできるだけ小さく、変更しない設計にします。 インターフェースとDTOだけを置き、実装や便利メソッドを混ぜないこと。 契約が頻繁に変わると、ホストとプラグインのバージョンずれが直ちに型不一致として現れます。

.NET Framework 同等のことをする場合は、 AppDomain による分離（MarshalByRefObject 越しのリモーティング）か、 LoadFrom ＋ AppDomain.AssemblyResolve ハンドラで 契約アセンブリをホスト側のものに強制する方法を取ります。 AppDomain分離は堅牢ですが、境界をまたぐ呼び出しがシリアライズを伴い、実装コストが高くなります。

10. 診断とトラブルシュート

10.1 まず入れておくべき自己診断コード

多重ロードは「起きてから調べる」と非常に手間がかかります。 起動時に一度だけ重複を検出してログに出す仕組みを入れておくと、調査時間が桁で変わります。

C# — 同名アセンブリの重複ロードを検出する
using System;
using System.Linq;
using System.Reflection;
using System.Runtime.Loader;   // .NET Core / .NET 5+ のみ

public static class AssemblyDiagnostics
{
    public static void ReportDuplicates(Action<string> log)
    {
        var groups = AppDomain.CurrentDomain.GetAssemblies()
            .Where(a => !a.IsDynamic)
            .GroupBy(a => a.GetName().Name, StringComparer.OrdinalIgnoreCase)
            .Where(g => g.Count() > 1);

        foreach (var g in groups)
        {
            log($"[重複ロード] {g.Key} が {g.Count()} 個ロードされています");

            foreach (var asm in g)
            {
                var config = asm.GetCustomAttribute<AssemblyConfigurationAttribute>()?.Configuration ?? "?";
#if NET
                var ctx = AssemblyLoadContext.GetLoadContext(asm)?.Name ?? "(既定)";
#else
                var ctx = "(.NET Framework)";
#endif
                log($"  Version={asm.GetName().Version} 構成={config} ALC={ctx}");
                log($"  MVID   ={asm.ManifestModule.ModuleVersionId}");
                log($"  場所   ={(string.IsNullOrEmpty(asm.Location) ? "(メモリ内)" : asm.Location)}");
            }
        }
    }
}

MVID（Module Version ID）はビルドごとに決まるGUIDです。 決定的ビルドなら「入力が同じなら同じMVID」になるため、 同名・同バージョンのDLLが本当に同じバイナリかどうかをMVIDで判定できます。 「同名同バージョンだけどMVIDが違う」＝ビルドが別、という決定的な証拠になります。

C# — ロード時にログを取る（原因のロード箇所を特定する）
// アプリのできるだけ早い段階で登録する
AppDomain.CurrentDomain.AssemblyLoad += (_, e) =>
{
    var name = e.LoadedAssembly.GetName();
    Console.WriteLine($"[LOAD] {name.Name} {name.Version} <- {e.LoadedAssembly.Location}");
    // 誰が読み込ませたかを追うにはスタックトレースも有効
    Console.WriteLine(Environment.StackTrace);
};

// 解決に失敗したときのフック（.NET Framework で特に有用）
AppDomain.CurrentDomain.AssemblyResolve += (_, e) =>
{
    Console.WriteLine($"[RESOLVE FAILED] {e.Name} (要求元: {e.RequestingAssembly?.FullName})");
    return null;
};

11. 実務チェックリスト

コードを書くとき

  • #if は本当に必要か。実行時の設定・DI・OperatingSystem.IsXxx() で代替できないか検討した
  • #if RELEASE と書いていない（RELEASE は定義されない。#if !DEBUG が正しい）
  • #if ブロックは短く、メソッドの内側に閉じている
  • public なメンバーの宣言そのものを #if で囲んでいない
  • シリアライズ対象・相互運用構造体のフィールドを #if で増減させていない
  • [Conditional] を付けたメソッドの引数に副作用を書いていない
  • 想定外のシンボル組み合わせを #error で塞いだ
  • 差分が10行を超えるなら、ファイル分割＋partial を検討した

ビルド設定

  • <DefineConstants> に $(DefineConstants); を付けて追記形式にした
  • CIで全構成・全ターゲットフレームワークをビルドしている（無効ブロックの腐敗検出）
  • MSB3277 / MSB3243（アセンブリ競合）警告が出ていない、または解消済み
  • .NET FW AutoGenerateBindingRedirects を有効にした
  • Deterministic が有効（既定）で、CIでは ContinuousIntegrationBuild も設定した
  • InformationalVersion にコミットハッシュ等の追跡情報を入れた

配布・デプロイ

  • 環境ごとに再ビルドせず、CIの成果物を全環境へ配っている（Build once, deploy many）
  • Releaseビルドであることを、配置後に AssemblyConfiguration で確認できる
  • DLLを1ファイルだけ手で差し替える運用になっていない（発行フォルダ単位／NuGet単位で配る）
  • マルチターゲットのDLLを、TFMを無視して手コピーしていない
  • .NET FW GACに古いバージョンが残っていないか確認した
  • デバッグ専用APIは別アセンブリに切り出し、本番に配置していない

多重ロード対策

  • 起動時に同名アセンブリの重複を検出してログに出す仕組みを入れた（10.1節）
  • ログにアセンブリの Location と MVID と構成を出している
  • プラグイン方式の場合、契約アセンブリをホストALCに一本化している
  • プラグイン側csprojで契約DLLを <Private>false</Private> にしてコピー除外した
  • Assembly.LoadFile をループで呼ぶ実装になっていない
  • ネイティブDLLのグローバル状態が、プラグイン間で共有されても問題ないことを確認した

12. 用語集

用語意味
条件付きコンパイルシンボル#if の条件に使う名前。真偽値としてのみ扱われ、値は持てない
DefineConstantsMSBuildのプロパティ。プロジェクト全体に効くシンボルを ; 区切りで指定する
TFM（Target Framework Moniker）net48、net8.0、netstandard2.0 のような対象フレームワークの識別子
IL（中間言語）C#コンパイラが出力する中間形式。DLLの中身はこれ。#if で捨てられたコードはここに存在しない
アセンブリのアイデンティティ単純名＋バージョン＋カルチャ＋公開キートークン。ビルド構成は含まれない
MVIDModule Version ID。ビルドごとに決まるGUID。同名同バージョンのバイナリ差を見分けられる
AppDomain.NET FW プロセス内の分離単位。.NET Core系では追加作成できない
AssemblyLoadContext（ALC）.NET Core+ アセンブリのロード単位。同名DLLを意図的に分離ロードできる
Loadコンテキスト／LoadFromコンテキスト.NET FW バインディングの3系統。LoadFile はどれにも属さず重複ロードを生む
GAC.NET FW グローバルアセンブリキャッシュ。強い名前のDLLの共有置き場。binより優先される
バインディングリダイレクト.NET FW 参照バージョンを別バージョンへ読み替える設定。.NET Core系では自動ロールフォワードが代替
決定的ビルド同じ入力から常に同じバイナリを出力するビルド。ハッシュ比較で同一性を検証できる
PDBデバッグシンボルファイル。行番号と変数名の対応表。あってもコード生成には影響しない

おわりに — 3つの原則

  1. 切り替えは、できるだけ実行時に寄せる。 同じバイナリを全環境に配れる状態は、それ自体が最大の事故防止策です。
  2. #if を使うなら、メソッドの内側に、短く、1箇所に。 公開APIの形だけは絶対に変えない。
  3. ログにアセンブリのパス・バージョン・構成・MVIDを出す。 多重ロードは「起きてから調べる」と最も高くつく問題です。出力しておけば10分で終わります。
